**基于纤程（Fiber）的 Job System 是一种任务调度架构：少量钉在核心上的工作线程负责执行，所有 job 都运行在纤程这种用户态执行上下文里；job 需要等待时，不阻塞线程，而是把自己所在的纤程挂起、换另一个纤程继续干活。最有名的实现来自 Naughty Dog 为 PS4 版《最后生还者 重制版》做的引擎改造。虚幻引擎的 Task Graph / `UE::Tasks` 不属于这一类，它们不用纤程。**

> 出处：Christian Gyrling, *Parallelizing the Naughty Dog Engine Using Fibers*, GDC 2015（演讲与幻灯片在 GDC Vault）。UE 部分对照 Epic 5.8 文档 *Tasks System*。本笔记原先写的是“虚幻引擎基于 Fiber 的 Job System”，这个说法不成立，下文把两者分开讲。

## 纤程是什么

纤程可以理解为“只有上下文、没有调度权的线程”：一块由程序自己分配的栈，加上一小块保存寄存器（程序计数器、栈指针、通用寄存器）的空间。纤程必须由某个线程来执行，切换完全是显式的：当前代码调用一次切换函数，把自己的寄存器存起来，载入目标纤程的寄存器，于是 CPU 就在目标纤程的栈上接着跑。PS4 上是 `sceFiberSwitch`，Windows 上是 `CreateFiber` / `SwitchToFiber`，也有 Boost.Context 这类跨平台库。

和线程比，纤程切换不进内核，不涉及调度器决策，也不会被换到别的核心上去，开销只是保存和恢复一组寄存器。和无栈协程（C++20 `co_await`）比，纤程有自己完整的栈，所以可以在任意深度的调用链里挂起，调用它的函数不需要做任何改写。这就是纤程在引擎里有吸引力的地方：现有的串行代码里随便哪一层插一句“等这批 job 做完”，都能工作。

## 为什么要用纤程做 Job System

普通 job system 最难处理的是“job 里要等别的 job”。例如一个动画 job 需要先把 64 个骨骼子任务分发出去，等它们全部完成再继续。有几种做法：

| 做法 | 问题 |
| --- | --- |
| 在 job 里阻塞等待（互斥量、事件） | 工作线程被占住不干活，线程数固定时很容易全部卡死 |
| 等待期间在当前栈上执行别的 job（busy-wait / work-while-waiting） | 被捡来的 job 可能又依赖正在等的 job，形成同一调用栈上的循环依赖；长 job 会让等待者迟迟不能恢复；栈越压越深 |
| 把 job 拆成“前半段 + 续体”，用依赖图描述 | 正确且高效，但要改写代码结构，旧代码迁移成本高 |
| 挂起当前纤程，线程换别的纤程执行 | 需要纤程基础设施，并且改变了同步原语的用法 |

Naughty Dog 选了最后一种。他们要把 PS3 时代以 SPU 为中心的引擎搬到 PS4 的多核 x86 上，并且跑到 60 fps，大量现有游戏代码需要尽快并行化，纤程让他们能“在 job 里任何地方等待”，而不必把整个引擎重写成依赖图。

## Naughty Dog 的设计

幻灯片里给出的配置：

| 项 | 取值 |
| --- | --- |
| 工作线程 | 6 个，每个锁定在一个 CPU 核心上 |
| 纤程 | 160 个：128 个 64 KiB 栈，32 个 512 KiB 栈 |
| Job 队列 | 3 个，低 / 普通 / 高优先级 |
| 任务窃取 | 不做 job stealing |
| 同步手段 | 原子计数器，是 job 之间唯一的同步方式 |
| 负载 | 《最后生还者 重制版》每帧约 800～1000 个 job |

核心规则是“线程是执行单元，纤程是上下文”，job 永远在某个纤程里执行。一次等待的过程大致是：job 发起一批子 job 时拿到一个原子计数器，初值等于子 job 数，每完成一个减一；job 调用 `ndjob::WaitForCounter(counter, 0)` 时，如果计数器还没归零，当前纤程就被放进等待列表，工作线程从空闲纤程池里取一个新纤程去执行队列里的下一个 job。计数器归零后，等待中的纤程重新变为可运行，之后可能在另一个工作线程上被恢复，纤程会在线程之间迁移。

```cpp
// 示意伪代码：演示 WaitForCounter 的语义，不是 Naughty Dog 的真实源码
void AnimateAllJob(JobData* Data)
{
    Counter* C = RunJobs(BoneJobs, NumBoneJobs); // 分发子 job，计数器 = NumBoneJobs
    WaitForCounter(C, 0);  // 计数器未归零：挂起当前纤程，线程转去跑别的 job
    // 恢复时可能已经在另一个工作线程上了
    BlendResults(Data);
}
```

把线程钉在核心上，是为了避免 OS 把工作线程在核心之间挪来挪去、避免内核线程的上下文切换在各核心之间引起连锁延迟。这套方案把“并发的基本单位”从线程换成了纤程，也带来了几个直接后果。

**系统同步原语不能再用。** 互斥量、信号量、条件变量都绑定到具体的 OS 线程，而纤程会在线程之间迁移：一个纤程在线程 A 上加锁，挂起后在线程 B 上恢复并解锁，OS 的互斥量会认为这是非法操作。Naughty Dog 的做法是几乎处处用原子自旋锁，持有时间较长的锁换成专门的 job mutex，拿不到锁时让当前 job 睡眠（挂起纤程），而不是自旋。

**线程局部存储（TLS）变得不可靠。** 编译器默认允许在一个函数内缓存 TLS 变量的地址，函数中途切换纤程、在别的线程上醒来后，拿到的还是原线程的 TLS 指针。幻灯片里提到当时 Clang 不支持“纤程安全”的 TLS 优化选项，他们的绕法是把 TLS 访问放进单独的 .cpp 文件，阻止编译器跨切换点缓存地址。

**栈大小要预先规划。** 每个纤程的栈是提前分配的固定大小，所以才有 64 KiB 和 512 KiB 两档，深递归或大局部数组的 job 必须显式放进大栈纤程。

**工具链要认识纤程。** 调试器得能像查看线程一样列出纤程、给纤程命名、显示当前在跑哪个 job，崩溃转储也要像保存线程一样保存每个纤程的调用栈。PS4 平台提供了这些支持，自己在 PC 上搭纤程系统时往往就没有这么顺手。

**不是所有代码都进 job。** 套接字、文件 IO、其他系统调用仍放在专门的 IO 系统线程里，这些线程像中断处理程序一样只负责读数据、投递新 job，从不在自己身上做重处理，否则一个阻塞调用就会占掉一个工作线程。

## 虚幻引擎是怎么做的

UE 的任务系统有两代接口，底下共用同一套调度器和工作线程：

| | Task Graph | Tasks System（`UE::Tasks`） |
| --- | --- | --- |
| 引入 | UE4 时代 | 5.0 |
| 典型入口 | `FFunctionGraphTask::CreateAndDispatchWhenReady`、`TGraphTask<T>`、`ENamedThreads` | `UE::Tasks::Launch`、`FTask` / `TTask<T>` |
| 依赖 | `FGraphEventRef` 前置事件 | prerequisites、`Prerequisites(A, B)` |
| 其他 | 可以把任务派到具名线程（GameThread 等） | 嵌套任务 `AddNested`、管道 `FPipe`、任务事件 `FTaskEvent`、优先级 `ETaskPriority` |

两者都不使用纤程：任务体就是一个在工作线程栈上执行、一口气跑到底的可调用对象。任务里需要等待时，UE 历史上的做法和纤程方案走的是不同的路：

- **5.5 以前：busy-waiting。** 等待时在当前栈上捡别的任务来执行。Epic 文档自己列出了它的问题：没有任务时空转浪费 CPU；捡到的无关任务可能反过来依赖正在等待的任务，在同一调用栈上形成无法解开的循环依赖，导致死锁；捡到长任务会让等待者迟迟不能恢复，造成卡顿；等待中的任务再等待，还可能栈溢出。这正是纤程方案想绕开的那组问题。
- **5.5 起：oversubscription。** busy-waiting 被标为废弃。线程等待时，系统唤醒额外的“备用线程”（standby threads）接替工作，等待结束、手上任务完成后再把它们停放起来。代价是多一些线程占用的内存，换来的是没有随机死锁和延迟问题。大多数等待函数已经带了 oversubscription 作用域，不需要程序员额外处理；Unreal Insights 里能看到 standby 线程和等待线程的 oversubscription 区间。

也就是说，同样是“任务里阻塞了怎么办”，Naughty Dog 用纤程把阻塞变成廉价的用户态切换，UE 则让 OS 线程真的阻塞，再用多开线程补上吞吐。UE 的选择保留了普通互斥量、TLS 和调试器的全部正常语义，适合一个面向大量第三方开发者、平台众多的通用引擎；纤程方案要求整个代码库遵守新的同步规则，更适合一个团队完全掌控代码的自研引擎。

UE 官方更推荐的是根本不在任务里等待，而是把依赖关系交给调度器：

```cpp
#include "Tasks/Task.h"

using namespace UE::Tasks;

void BuildFrameData()
{
	// 不好：父任务占着工作线程等子任务
	FTask Bad = Launch(UE_SOURCE_LOCATION, []
	{
		FTask Child = Launch(UE_SOURCE_LOCATION, [] { /* 子工作 */ });
		Child.Wait();
	});

	// 好：嵌套任务。父任务体立即返回，父任务在子任务完成后才算完成
	FTask Parent = Launch(UE_SOURCE_LOCATION, []
	{
		FTask Child = Launch(UE_SOURCE_LOCATION, [] { /* 子工作 */ });
		AddNested(Child);
	});

	// 好：前置依赖。C 只在 A、B 都完成后才被调度，期间不占用任何线程
	FTask A = Launch(UE_SOURCE_LOCATION, [] { /* ... */ });
	FTask B = Launch(UE_SOURCE_LOCATION, [] { /* ... */ });
	FTask C = Launch(UE_SOURCE_LOCATION, [] { /* 使用 A、B 的结果 */ }, Prerequisites(A, B));
}
```

`AddNested` 只能在任务体内部调用，否则会断言。对需要串行访问的共享资源，UE 提供 `FPipe`：同一个 pipe 上启动的任务保证不会并发执行，Epic 文档把 pipe 比作由工作线程执行的“绿色线程”，这是 UE 里概念上最接近纤程调度的东西，但它依然是在调度层面串行化任务，不是保存和恢复执行栈。

## 容易踩的坑

**把“纤程”当成 UE 的实现细节去写代码。** UE 的任务不会在等待时被挂起再换线程恢复，所以也不存在 TLS 失效之类的纤程问题；反过来，UE 的任务里阻塞一定会占住一个线程（5.5 起由备用线程补位），不能指望它像纤程那样“免费”。

**在纤程系统里继续用 OS 互斥量。** 纤程在线程 A 上加锁、在线程 B 上解锁，行为未定义。自研纤程系统要从一开始就规定锁的用法。

**纤程栈开太小。** 固定栈没有保护页时，溢出会直接踩坏相邻内存，表现为毫不相干的崩溃。

**在 5.5 以前的 UE 里依赖 busy-waiting。** 老代码在任务里 `Wait()` 能跑，但偶发死锁和卡顿往往就是它引起的，升级到 5.5 后行为会变化，Insights 里会出现 standby 线程。
