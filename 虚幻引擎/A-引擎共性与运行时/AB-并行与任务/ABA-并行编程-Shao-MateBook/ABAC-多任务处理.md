**多任务处理（Multitasking）指一个系统在同一段时间里推进多个任务的能力。按“谁决定什么时候切换任务”分成两类：由调度器强行打断的抢占式（Preemptive），和由任务自己让出执行权的协作式（Cooperative，也叫非抢占式）。现代桌面和主机操作系统对线程一律用抢占式调度，而游戏引擎在线程之上又会搭一层协作式的任务、协程或纤程。**

> 参考：Silberschatz《Operating System Concepts》CPU 调度一章；UE 部分对照 Epic 5.x 文档 *Tasks System*。

## 切换权在谁手里

多任务的核心问题只有一个：CPU 核心数远少于想要同时推进的工作数，必须轮流用。轮流就要切换，切换就要回答“什么时候切、由谁来切”。

**抢占式**把这个决定交给操作系统。内核靠定时器中断定期拿回控制权，看当前线程的时间片（time slice / quantum）用完没有、有没有优先级更高的线程就绪，需要的话就把当前线程的寄存器、程序计数器、栈指针保存进它的内核数据结构，再装入下一个线程的上下文。被切走的线程对此毫不知情，它可能停在任意一条指令上。

**协作式**则要求任务自己调用某个“让出”（yield）操作，把执行权交回调度器。调度器不会也无法中途打断一个不肯让出的任务。切换点因此是确定的、写在代码里的。

| | 抢占式 | 协作式 |
| --- | --- | --- |
| 谁触发切换 | 调度器（定时器中断、更高优先级就绪、阻塞系统调用） | 任务自己（yield、await、等待某个计数器） |
| 切换点 | 任意指令之间 | 代码里显式写出的位置 |
| 一个任务死循环 | 其他任务照样运行 | 整个调度器卡死 |
| 共享数据保护 | 几乎任何共享写都要加锁或用原子操作 | 两个切换点之间的代码天然不会被同一调度器上的其他任务打断 |
| 切换成本 | 陷入内核、保存完整上下文、可能换核导致缓存失效 | 用户态保存少量寄存器，或仅仅是函数返回 |
| 典型实例 | Windows NT 系、Linux、macOS、PS/Xbox 系统的线程调度 | Windows 3.x、Mac OS 9 以前的进程调度；协程、纤程、UE 的任务 |

历史上桌面系统都走过从协作到抢占的路。Windows 3.x 的应用程序必须频繁回到消息循环把控制权交还系统，某个程序卡住，整个桌面就一起卡住；Windows 95 对 32 位程序改为抢占式，经典 Mac OS 直到 Mac OS X 才换成抢占式内核。原因很直接：操作系统要同时跑互不信任、质量参差的程序，不可能指望每个程序都守规矩。

## 抢占式的代价

抢占式换来的是鲁棒性和响应性：任何线程都不能独占 CPU，输入、音频这类高优先级线程总能及时拿到时间片。代价有两部分。

一是切换本身的开销。一次线程上下文切换要进出内核，保存和恢复整套寄存器，如果新线程被调度到别的核心，原来热在 L1/L2 里的数据全部作废。单次开销通常在微秒量级，但游戏一帧只有 16.6 ms 甚至 8.3 ms，线程多、切换频繁时这部分就会显形。

二是正确性上的负担。线程可能在任何两条指令之间被打断，所以 `Counter++` 这种看上去一步的操作（读、加、写三步）在两个线程之间就会丢失更新。所有共享可变数据都必须用互斥锁、原子操作或者无锁结构保护，而锁又带来死锁、优先级反转、锁竞争。

## 协作式的代价

协作式的切换可以极便宜：纤程切换只需保存几个寄存器、换一下栈指针；无栈协程的“切换”干脆就是函数返回，状态存在编译器生成的状态机里。而且切换点可预测，在同一个调度线程上，两个 yield 之间的代码不会被别的任务插进来，很多同步问题自然消失。

问题在于它把系统的公平性押在每个任务身上。一个任务算得太久不 yield，同一线程上排队的所有任务都得等；一个任务在里面调用了阻塞的系统调用（比如同步读文件），整个工作线程就被挂起。协作式调度也不能单独解决多核问题：它只决定一个线程内部怎么轮流，要用满多核，还是得有多个真正的 OS 线程。

## 游戏引擎里两者怎么叠在一起

实际的引擎是“下层抢占、上层协作”的两层结构。操作系统以抢占方式调度少量长期存在的线程：游戏线程、渲染线程、RHI 线程、音频线程，以及一组工作线程。引擎再在工作线程上用自己的任务调度器运行大量短小的任务，任务之间的切换是协作式的：一个任务一旦开始，就在这个工作线程上一直运行到结束，调度器不会中途把它换下来。这样既保留了 OS 抢占带来的系统级安全，又把高频的任务切换留在用户态。

UE 的 Task Graph 和 5.0 起的 `UE::Tasks` 就是这种模型。任务体是一个可调用对象，由工作线程取出执行，调度器不会中途暂停它。等待另一个任务时，如果直接调 `Wait()`，当前工作线程就阻塞了；因此 Epic 文档一再建议用前置依赖（prerequisites）描述任务之间的先后关系，而不是在任务里等。关于 UE 如何处理“任务里必须等待”这种情况（5.5 以前的 busy-waiting、5.5 起的 oversubscription），以及它和 Naughty Dog 纤程方案的区别，见 [[ABBAA-基于Fiber的Job System]]。

协作式在游戏逻辑层也随处可见，只是通常不叫这个名字：

| 形式 | 例子 | 让出的方式 |
| --- | --- | --- |
| 协程 | Unity 的 `IEnumerator` 协程、C++20 `co_await` | `yield return` / `co_await` |
| 潜伏动作（Latent Action） | UE 蓝图的 `Delay`、`AI MoveTo` 等带时钟图标的节点 | 节点挂起执行流，由 `FLatentActionManager` 每帧检查是否完成 |
| 状态机式的分帧处理 | 每帧只处理 N 个对象的时间切片循环 | 函数自己记住进度并返回 |
| 纤程 | Naughty Dog 引擎的 job | 等待计数器时切换到别的纤程 |

这些机制都跑在游戏线程或某个工作线程内部，它们的“让出”只影响同一个调度器里的其他任务，不影响 OS 对线程的抢占。所以蓝图里一个 `Delay` 并不会让游戏线程休眠，而一个不让出的超长循环照样会把整帧卡住，这正是协作式调度的典型症状。

## 容易踩的坑

**以为协作式就不用加锁。** 只有在同一个调度线程上、两个让出点之间的代码才不会被打断。UE 的任务、Unity 的 Job 会被分到多个工作线程上真正并行地跑，任务之间共享的数据仍然要同步，或者用 `UE::Tasks::FPipe` 把访问串行化。

**在任务里做阻塞操作。** 同步 IO、`Sleep`、长时间持有互斥锁，都会让一个工作线程白白闲置。长时间运行、跨多帧的工作更适合独立的 `FRunnable` 线程，这是 Epic 员工在论坛上对 Task Graph 的一贯建议。

**把协程当并行。** Unity 协程、UE 的潜伏动作默认都在游戏线程上推进，它们让代码写起来像“同时进行”，但不会多用一个核心。
